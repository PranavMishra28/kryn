# KRYN status — supervised v1 candidate

KRYN's next product target is a local-first **supervised coding workspace** for native Apple Silicon macOS 26/27. OpenCode remains the harness; the installed Qwen3.5-9B-6bit model, oMLX 0.6.4 runtime, guarded 96K configured context, one active local generation and current resource guard remain frozen. The published [v0.2.0 preview](https://github.com/PranavMishra28/kryn/releases/tag/v0.2.0) is still the latest public release. **No v1 release has been qualified or published.** [Use KRYN](README.md) · [Architecture](docs/architecture.md) · [Supervised v1 contract](docs/v1-qualification.md).

## Product decision

The 9B local profile is the strongest profile yet shown sustainable on this normally occupied 48-GiB Mac. The 35B profiles repeatedly reached the unchanged memory guard; a 14B/49K profile passed one small task but was guard-stopped during a harder UI trial. A shorter context has not shown enough accepted-work benefit to replace the configured 96K. No paid external provider is configured or authorized. Other providers remain an explicit OpenCode choice with remote-data and possible cost implications. [Model decision receipt](evals/history/2026-10-01-daily-envelope-model-decision.json) · [14B screen](evals/history/2026-10-01-ministral14-daily-screen.json).

The local 9B did **not** achieve repeatable autonomous UI acceptance: the Acceptance Controller and requirement/evidence experiments each produced 0/3 accepted applications. The controller did block false success claims; it did not repair the applications. A fresh Task12 repeat again passed backend checks while shipping a JavaScript syntax error and falsely claiming browser completion; its independent browser oracle failed immediately. A later staged supervised Task12 run produced a working app only after model feedback and operator fixes; its fresh Reviewer missed two browser-proven defects. KRYN v1 must not promise autonomous application building, independent Reviewer authority, frontier parity or useful reasoning across all 96K tokens. The frozen [autonomous evaluation protocol](docs/evaluation.md) and [failed receipts](docs/history.md) remain a separate research track. [Controller experiment](evals/history/2026-10-01-managed-acceptance-a.json) · [Requirement evidence](evals/history/2026-10-01-requirement-evidence-b.json) · [Autonomous UI gate](evals/history/2026-10-01-autonomous-ui-quality-gate.json) · [Fresh repeat](evals/history/2026-10-02-supervised-v1-endurance-repeat-failure.json) · [Staged screen](evals/history/2026-10-02-supervised-v1-staged-task12.json).

## Release sequence

Keep public tags and version bumps paused while private supervised-product screens are open. Once those screens pass, prepare and review a private 1.0.0 release PR, merge green code, then build the exact clean-main wheel and rerun all supervised gates from those bytes. Publish the tag and assets only after that final-artifact qualification; verify anonymous installation afterward. A prior candidate result cannot retroactively turn an unrun final-artifact gate into a pass. See the [release runbook](docs/releasing.md).

The superseded autonomous-gate table and detailed earlier narrative remain in [immutable Git history at `aef8188`](https://github.com/PranavMishra28/kryn/blob/aef8188/plan.md). Primary receipts and frozen fixtures remain unchanged under `evals/history/` and `evals/`; [historical evidence](docs/history.md) indexes earlier narratives. The optional learning worker is paused and has no proved cross-project benefit; private incident capture and source/check evidence aid supervised diagnosis without automatically changing product code or policy.
