# Releasing KRYN

The public release gate is [supervised v1 qualification](v1-qualification.md). The [status table](../plan.md) must link actual final-artifact receipts for every required row. Frozen autonomous/UI research failures remain disclosed; they are not a supervised-v1 pass criterion.

1. Prepare a focused release PR with the intended version in `pyproject.toml` and `src/kryn/__init__.py`, exact README installation commands, changelog, security and third-party notices. Keep public tags paused while any supervised gate is open. Review the tracked tree and Git history with a redacting secret scanner; inspect every finding without copying raw secrets into issues or commits. Review direct and transitive dependency resolutions, including the browser lock and optional install phases; a direct version pin alone is not a complete transitive lock.
2. Run `make check`, `make package-smoke` and the appropriate live qualification. Review the PR diff, pinned dependency identities, license terms, permissions and CI result. Merge only green reviewed code. Do not create the tag from a dirty checkout or a private candidate wheel.
3. On the final clean `main` commit, build with `python3 -B build_package.py --out-dir dist`. Record the commit and `dist/SHA256SUMS`; inspect the wheel manifest and verify `shasum -a 256 -c dist/SHA256SUMS`. Install that exact local wheel through the supported owner workflow, verify startup, terminal and GUI use, saved-session continuation, update/rollback and reactivation. If any gate fails, fix it in a new PR and restart final-artifact checks from the new commit.
4. Tag the exact qualified commit as `vX.Y.Z`, push the tag, then publish the wheel, `install-kryn.py` and `SHA256SUMS` as one GitHub release. Check that the published assets equal the qualified local hashes. The release description must state supervised scope, supported hardware, known autonomous limits and rollback instructions.
5. From an anonymous HTTP client, download the published installer and assets over HTTPS, verify hashes, and perform a fresh install or update using the documented command. Record the result in [historical evidence](history.md). If publication or anonymous verification fails, leave the release marked unqualified and repair it explicitly.

The wheel builder rejects dirty source unless `--candidate` is passed. Candidate builds are for private checks only and must never be published. The installer verifies HTTPS downloads, release checksum, curated payload hashes and pinned dependencies; checksum assets rely on the authenticated publisher and are not independent signatures. Preserve previous tags for reproducibility and rollback unless there is a documented security reason to remove one.
