# KRYN evaluation and model decisions

## Native stack decision

OpenCode is the only agent harness: it owns sessions, Ask/Plan/Agent, model and effort selection, permission decisions, tools, background child sessions, [skills](https://opencode.ai/v2/docs/skills), [MCP servers](https://opencode.ai/v2/docs/mcp-servers), and [compaction](https://opencode.ai/v2/docs/compaction). The local provider sends OpenAI-compatible requests to oMLX, which owns model loading, inference, cache, and its process-memory guard. KRYN adds only the owned launch/install boundary, resource checks, bounded continuity and incident evidence. The configured `/call` and Reviewer/Browse children use [OpenCode's native agent and command mechanisms](https://opencode.ai/v2/docs/agents); they do not make one local model generate in parallel. Project skills and external providers remain OpenCode features, subject to the selected model, credentials, permissions and service availability.

For a model or runtime upgrade, first prove that the same native tools work and the model finishes useful tasks under the Mac's host guard. Publisher benchmarks compare other quantizations, contexts and harnesses; they are candidate-selection hints, not KRYN acceptance. Do not add a second orchestrator, extra prompt rules, or speculative MCP servers to compensate for a failing model trial. Preserve the current daily profile until a challenger clears the gates below.

The installed 9B/96K profile is the daily baseline, not a qualified frontier baseline. A model publisher's coding score, a configured context number, or a completed agent turn cannot establish KRYN task quality. Keep the [frozen TaskboardLite suite](../evals/README.md) and its SHA256 manifest unchanged; the [fresh review-queue task](../evals/fresh_review_queue/README.md) checks API preservation, browser behavior and long-workflow evidence outside the candidate workspace.

## Run a comparable trial

1. Freeze the KRYN source revision, model artifact hashes, OpenCode/oMLX versions, configuration, available tools and permissions. Record the context/output reservation and guard. Prepare a new disposable run with `python3 -B evals/bench.py prepare 02 UNIQUE-ID`; never reuse a failed workspace or show the candidate its oracle.
2. Run the normal native OpenCode agent in the printed workspace, submitting `TASK.md` verbatim. For a scripted native turn with the owned runtime already running, use `python3 -B tools/run_native_trial.py evals/runs/UNIQUE-ID --stage first --agent agent --guard-resources`. Its trace is a run record, not a grade. For a different local model, use all four `--replacement-model-id`, `--replacement-context`, `--replacement-output` and `--replacement-guard-gib` flags; the driver checks the exact served model and guard before prompting. Follow [the isolated challenger lifecycle](../CONTRIBUTING.md) so a trial does not rewrite the owner's oMLX settings.
3. Grade outside the candidate workspace with `python3 -B evals/bench.py grade UNIQUE-ID`. Inspect `grade.json`, actual native tool results and any required external `review.json`. A browser or long-workflow task remains partial without its independent browser/restart/compaction review, even when code checks pass. Keep every failed run and timeout.

Compare **one factor at a time**: model/quantization, context and guard, OpenCode/plugin behavior, or provider. If a challenger requires a smaller context, also run the incumbent at that feasible context; otherwise report the result as a whole-profile comparison, not a model gain. Compare the same prompts and checks on tasks 02/03/06/09, then the fresh review-queue task. Alternate arm order and run three matched repetitions for short tasks. Keep cold and warm cache, power state and foreground load distinct. Three repetitions can reveal obvious regressions but cannot establish statistical superiority.

For each run retain independent pass/fail by acceptance criterion, truthful or false completion claims, Reviewer findings verified against current source, interventions, useful active duration, first-token and total latency, input/output/cache token counts, peak process memory, host pressure, swap delta, guard stops, config/model hashes and raw trace location. Mark absent telemetry **unavailable**. A free provider's HTTP 403 or quota failure is an unavailable or failed route, not zero-cost capacity. Do not blend a local result with a remote provider or claim a SWE-bench/Terminal-Bench leaderboard score from these fixtures.

Only consider a new daily default after it completes a fresh coding/UI task with independent source and browser checks, preserves existing behavior, reports accurate review findings, survives two actual compactions and a process restart with the correct next action, runs useful sustained work under the guard, and passes owner install/rollback. KRYN's current 9B profile has **not** passed all those gates. Until a challenger clears them, keep the known installed profile and label candidates experimental.

Incident capture is event-driven: preserve the real failed run, reproduce its symptom with an independent check, change the owning layer, rerun that case and adjacent frozen cases, then accept or revert from observed results. `kryn improve failures` is a private failure index; it does not diagnose or automatically promote code, prompts or weights. Protect unseen holdouts outside candidate workspaces. [SWE-bench](https://github.com/SWE-bench/SWE-bench) and [Terminal-Bench](https://github.com/harbor-framework/terminal-bench) inform outcome-based task design; [METR's long-task methodology](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/) motivates tracking useful active duration and reliability across task lengths.
