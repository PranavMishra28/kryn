# KRYN evaluation and model decisions

## Native stack decision

OpenCode is the only agent harness: it owns sessions, Ask/Plan/Agent, model and effort selection, permission decisions, tools, background child sessions, [skills](https://opencode.ai/v2/docs/skills), [MCP servers](https://opencode.ai/v2/docs/mcp-servers), and [compaction](https://opencode.ai/v2/docs/compaction). The local provider sends OpenAI-compatible requests to oMLX, which owns model loading, inference, cache, and its process-memory guard. KRYN adds only the owned launch/install boundary, resource checks, bounded continuity and incident evidence. The configured `/call` and Reviewer/Browse children use [OpenCode's native agent and command mechanisms](https://opencode.ai/v2/docs/agents); they do not make one local model generate in parallel. Project skills and external providers remain OpenCode features, subject to the selected model, credentials, permissions and service availability.

The installed 9B profile is the settled daily choice. Do not reopen model, quantization, or context selection for small benchmark differences or new release announcements. Reconsider it only when a concrete challenger materially improves independently accepted coding/UI work with the same native tools and clears the review, continuity, resource, and install/rollback gates below. Publisher benchmarks are candidate-selection hints, not KRYN acceptance. Do not add a second orchestrator, extra prompt rules, or speculative MCP servers to compensate for a failing model trial.

The installed 9B/96K profile is the daily baseline, not a qualified frontier baseline. A model publisher's coding score, a configured context number, or a completed agent turn cannot establish KRYN task quality. Keep the [frozen TaskboardLite suite](../evals/README.md) and its SHA256 manifest unchanged; the [fresh review-queue task](../evals/fresh_review_queue/README.md) checks API preservation, browser behavior and long-workflow evidence outside the candidate workspace.

The [research protocol](../research/PROTOCOL.md) and [development pilot](../research/DEVELOPMENT.md) track the separate same-model harness study and its open gates. Those public-fixture results do not change the installed v1.0.0 profile.
The [2026-10-04 local-only campaign checkpoint](../research/LOCAL_CAMPAIGN_2026-10-04.md) reports an interrupted external benchmark and one matched pair; it is not an autonomous qualification.

“Frontier-equivalent” would require a named frontier agent comparator on the same independently graded tasks and comparable tools, budgets and repetitions. Internal passes alone could support a bounded autonomous-workflow claim, not general parity. No matched frontier comparator is available under the current free/local-only constraint, and KRYN's own required workflow gates still fail; neither claim is qualified.

## Run a comparable trial

1. Freeze the KRYN source revision, model artifact hashes, OpenCode/oMLX versions, configuration, available tools and permissions. Record the context/output reservation and guard. Prepare a new disposable run with `python3 -B evals/bench.py prepare 02 UNIQUE-ID`; never reuse a failed workspace or show the candidate its oracle.
2. Run the normal native OpenCode agent in the printed workspace, submitting `TASK.md` verbatim. For a scripted native turn with the owned runtime already running, use `python3 -B tools/run_native_trial.py evals/runs/UNIQUE-ID --stage first --agent agent --guard-resources`. Its trace is a run record, not a grade. For a different local model, use all four `--replacement-model-id`, `--replacement-context`, `--replacement-output` and `--replacement-guard-gib` flags; the driver checks the exact served model and guard before prompting. Follow [the isolated challenger lifecycle](../CONTRIBUTING.md) so a trial does not rewrite the owner's oMLX settings.
3. Grade outside the candidate workspace with `python3 -B evals/bench.py grade UNIQUE-ID`. Inspect `grade.json`, actual native tool results and any required external `review.json`. A browser or long-workflow task remains partial without its independent browser/restart/compaction review, even when code checks pass. Keep every failed run and timeout.

Compare **one factor at a time**: model/quantization, context and guard, OpenCode/plugin behavior, or provider. If a challenger requires a smaller context, also run the incumbent at that feasible context; otherwise report the result as a whole-profile comparison, not a model gain. Compare the same prompts and checks on tasks 02/03/06/09, then the fresh review-queue task. Alternate arm order and run three matched repetitions for short tasks. Keep cold and warm cache, power state and foreground load distinct. Three repetitions can reveal obvious regressions but cannot establish statistical superiority.

For each run retain independent pass/fail by acceptance criterion, truthful or false completion claims, Reviewer findings verified against current source, interventions, useful active duration, first-token and total latency, input/output/cache token counts, peak process memory, host pressure, swap delta, guard stops, config/model hashes and raw trace location. Mark absent telemetry **unavailable**. A free provider's HTTP 403 or quota failure is an unavailable or failed route, not zero-cost capacity. Do not blend a local result with a remote provider or claim a SWE-bench/Terminal-Bench leaderboard score from these fixtures.

Only consider a new daily default after it completes a fresh coding/UI task with independent source and browser checks, preserves existing behavior, reports accurate review findings, survives two actual compactions and a process restart with the correct next action, runs useful sustained work under the guard, and passes owner install/rollback. KRYN's current 9B profile has **not** passed all those gates. Until a challenger clears them, keep the known installed profile and label candidates experimental.

## Fail-closed selection rubric

Treat TaskboardLite as a **development regression set**: its public prompts and repeated use can reveal weaknesses but cannot serve as an unseen holdout. Freeze a new private, human-reviewed task before inspecting candidate output. Keep its solution and browser/API oracle outside the candidate workspace; publish the task only after the selection decision. Validate that the reference solution passes and a deliberately broken seed fails. This follows the [separate-verifier design used by Terminal-Bench](https://github.com/harbor-framework/terminal-bench/blob/main/docs/task-template.toml) without introducing another KRYN agent harness.

Record one row per attempt, including aborted and timed-out runs. A row is **accepted** only when the exact frozen task, native config/model hashes, complete tool trace, current source/evaluator-bound check receipts (`evals/observe.py`), independent UI/API review when applicable, and green resource samples are present. Missing or stale evidence is **unqualified**, not a pass. A false completion claim, lost next action after compaction/restart, failed browser/API criterion, protocol failure, host warning, or excessive swap is a hard failure; latency and token throughput cannot offset it. Keep intervention counts separate so an operator repair cannot be reported as an autonomous pass.

Compare matched arms on the same task version, context budget, tools, permissions, time limit and foreground/power condition. Alternate order, use three paired repetitions for short tasks, and report pass counts plus the median and range of useful active time; with only three trials, do not infer a stable win from a small timing gap. Run a fresh coding/UI holdout, two real compactions, restart, sustained work, and owner install/rollback for the proposed default. Choose the fastest and most capable **reliably accepted** profile; if none passes, retain the existing daily profile and expose the stronger candidate only as experimental. This controls for the [infrastructure noise documented in agentic coding evals](https://www.anthropic.com/engineering/infrastructure-noise) and grades the [environment outcome rather than the agent's success claim](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

Incident capture is event-driven: preserve the real failed run, reproduce its symptom with an independent check, change the owning layer, rerun that case and adjacent frozen cases, then accept or revert from observed results. `kryn improve failures` is a private failure index; it does not diagnose or automatically promote code, prompts or weights. Protect unseen holdouts outside candidate workspaces. [SWE-bench](https://github.com/SWE-bench/SWE-bench) and [Terminal-Bench](https://github.com/harbor-framework/terminal-bench) inform outcome-based task design; [METR's long-task methodology](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/) motivates tracking useful active duration and reliability across task lengths.

The application-quality loop follows the narrow common lesson from [OpenAI's harness engineering](https://openai.com/index/harness-engineering/) and [Anthropic's long-running application harness](https://www.anthropic.com/engineering/harness-design-long-running-apps): make the app runnable, inspect its rendered behavior, and feed observed failures back into the same native agent session. A tool call or self-review is still not independent acceptance. KRYN uses [OpenCode's own plugin and synthetic-message API](https://opencode.ai/v2/docs/build/plugins) for any bounded continuation; it does not add a second agent framework.

For a **development-only managed trial**, pass `--managed-acceptance evals/runs/UNIQUE-ID/acceptance.json` to `tools/run_native_trial.py` alongside `--guard-resources`. The evaluator-owned JSON lists original requirements, check commands and affected path patterns outside the Agent workspace. The controller waits for native idle, runs current source/API/browser checks, invalidates affected passes after edits, and allows at most two same-session repairs. Its `accepted` or `blocked` state is authoritative for that trial; the model's prose is not. Run the full independent checker again afterward. Check selection for an arbitrary user repository is not automatic, and these failed development runs do not qualify an installed autonomous mode.

Planner/builder/evaluator graphs are a useful [research pattern](https://www.anthropic.com/engineering/harness-design-long-running-apps), but KRYN already has these roles through native OpenCode Plan, Agent, Browse and Reviewer. Adding another graph cannot substitute for a reliable evaluator. In matched local Reviewer trials, a [scoped Git-diff tool](../evals/history/2026-09-30-public-distribution-and-reviewer-diagnostic.json) was unused and a [lower-temperature setting](../evals/history/2026-10-01-reviewer-temperature-rejection.json) produced repetition until the output limit, without a verdict. Both candidates were reverted. Keep executable API/browser contracts outside the candidate workspace as the acceptance authority, and audit prompts/oracles for ambiguity and coverage before attributing every failure to the model; [OpenAI's benchmark audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/) documents why that matters. A new orchestration layer needs a demonstrated pass on fresh independent work before adoption.
