# Fresh task: review queue

Extend this disposable TaskboardLite project with a review queue for time entries. Work in ordered PLAN, BUILD, CHECK, AUDIT and HANDOFF stages. In PLAN, inspect the current code and record the acceptance criteria before editing. In BUILD, implement the backend and browser flow using only Python's standard library and the existing plain web files. Keep the original CSV format, entries API responses, seed data and existing tests intact.

Every entry starts pending, including entries imported or created later. Add `GET /api/review`, returning a list of `{ "id": string, "reviewed": boolean }` in ID order for every current entry. Add `POST /api/review` accepting one JSON object with exactly `id` and `reviewed`. The ID must exist and `reviewed` must be a JSON boolean. A valid request persists the state and returns HTTP 200 with the same two fields. Missing/unknown IDs, malformed JSON, extra fields and nonboolean values return HTTP 400 JSON with an `error`, without changing any review state. Repeating a valid request is safe. The existing one-shot `.fail-next` marker must cause HTTP 503 before a review write, so a manual retry is safe.

In the browser, show each entry's review state and a button named **Mark reviewed** or **Return to pending**, as appropriate. Provide a select labeled **Review status** with **All**, **Pending** and **Reviewed** options. Changing it filters the visible rows without changing stored data. After a successful action, update the row and filter view; reload must show the persisted state. After a 503, show a visible accessible error, retain the user's current filter and the row's actionable state, and let the user retry manually. Do not silently retry. Render stored project text as text, never executable markup; do not use `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `eval` in the web client. Keep the existing entry form, import, edit, export and responsive layout working.

In CHECK, run the existing tests and inspect the changed source. Start the app with a disposable database and use a real browser at 390×844 and 1280×800 to verify filtering, action/reload, one injected 503 and manual retry, visible feedback, screenshots, console and network. Keep the server alive across browser actions and reloads. In AUDIT, give a fresh read-only reviewer the criteria, current diff and actual check output; retain findings with file and line evidence. In HANDOFF, record the completed criteria, failed or unverified checks, evidence paths and exact next action. Do not report browser acceptance or review as passed from your own assertion alone.
